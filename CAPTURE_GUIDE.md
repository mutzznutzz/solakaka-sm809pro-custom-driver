# Capture the official wheel configuration

## What we already know

The original application is a local desktop HID configurator, not a backend server. It writes configuration through USB HID feature reports. Normal scrolling is then generated by the mouse as HID input. Rotation and middle click have separate mappings.

Robin's working restored profile contains:

```ini
Key16Name=Wheel Up
Key16Value=102000
Key17Name=Wheel Down
Key17Value=104000
```

The full keymap is 18 three-byte entries. Report ID is 06, command is 01, first subcommand is 02, second subcommand is 12 (hex). Each write has 32 bytes INCLUDING the leading report ID. The sequence and checksum change, so the six wheel bytes alone are not a complete replayable report.

| Byte offset, including report ID | Meaning |
| --- | --- |
| 0 | Report ID: 06 |
| 1 | Mapping command: 01 |
| 2 | Sequence counter |
| 3 | Subcommand: 02 or 12 |
| 4 | Checksum |
| 5-31 | Nine three-byte mappings |

The second report contains slots 9-17. Wheel Up is bytes 26-28; Wheel Down is bytes 29-31. For normal scrolling the last six bytes are `10 20 00 10 40 00`. Checksum is the sum of all other 31 report bytes modulo 256.

The 18-slot writer was located in the installed official GamingMS.exe at VA 0x00437F60, with writes at 0x004382FF and the second subcommand set at 0x004383BF. Installed SHA-256: `0cb4fd2ebd8c9d9470a1563206b3793f58b0fece84b17e02bfe4cd0cef93627f`. These addresses are build-specific. This is static evidence, not a live capture.

## Cleanest live capture: Wireshark with USBPcap

1. Keep the original custom executable closed. Use the working manufacturer app at `C:\Program Files\SM809pro Mouse Full\GamingMS.exe`. Export your working profile first. There is no need to reinstall the manufacturer software each time; Restore repaired the configuration.
2. Install Wireshark and USBPcap using their official downloads. USBPcap is the Windows capture driver; follow its restart requirement if prompted. Don't install a replacement WinUSB/libusb driver for the mouse.
3. Run USBPcapCMD from its installation folder to identify the root hub containing the mouse, VID `04F3`, PID `809E`. Select the corresponding USBPcap interface in Wireshark. Keep your laptop touchpad available while reconnecting the mouse.
4. Start capture BEFORE reconnecting the mouse's USB cable. Reconnect it to the same port so the capture includes its device descriptors. In the descriptor packet, confirm VID/PID and note the USB bus ID and device address. Address can change after reconnection.
5. Open the manufacturer app. Record the time, click Restore and Apply if applicable. If it sends only a reset command or no mapping reports because settings already match, temporarily change one unused side button to a benign action and Apply. Don't change left click. Then Restore and Apply again to return to the working defaults. Keep the capture short and stop it afterward.
6. Save the ORIGINAL capture as `official-restore.pcapng`, retaining all packets. A selected root-hub capture may contain other devices' traffic; avoid typing passwords during capture and inspect it before sharing publicly.
7. Filter to your mouse using the numeric values from step 4. For example, if bus is 1 and address is 7:

```text
usb.bus_id == 1 && usb.device_address == 7
```

Then narrow the visible results to HID SET_REPORT requests for feature report 6:

```text
usb.bus_id == 1 && usb.device_address == 7 && usb.setup.bRequest == 0x09 && usb.setup.wValue == 0x0306
```

Here 0x0306 is Feature report type 3 plus report ID 6. Do not filter only on VID/PID for the whole session: those fields usually appear in enumeration descriptors, not every data packet.

8. Expand the USB setup/data details. Look for the report payload starting `06 01`, subcommand `02` or `12` at report byte 3, and length 32. Select the report DATA field and use Copy > Value / Hex Stream, depending on Wireshark version. Copy the 32 report bytes, not the USBPcap/USB headers or a formatted multi-column hex dump. Payload field names and data-stage presentation vary; if the request filter hides the data, use the bus/device filter and inspect the associated control-transfer data stage. Preserve the original capture rather than guessing missing bytes.
9. Save both complete mapping reports and their frame numbers. A reset command starting `06 0F` is a different operation; it is not the two keymap packets. If no mapping reports appear, share the capture for inspection rather than assuming they don't exist.
10. To verify actual scrolling, take a short separate capture while turning the wheel several notches up and down and pressing middle click. Label those actions/times. Those are interrupt INPUT reports, not the feature configuration reports above. This confirms that rotation events still reach Windows after writing settings.

## Decode a copied report without sending it

From the project directory:

```powershell
python tools/inspect_key_report.py --hex "PASTE THE 32 REPORT BYTES HERE"
```

Or save one hex report in a text file:

```powershell
python tools/inspect_key_report.py --file official-second-report.txt
```

The tool validates the length, header and checksum and lists the nine slots. For the second keymap packet it also reports whether slots 16 and 17 contain the working normal-scroll values. It performs no USB access. Keep frame numbers and capture context too: syntactically valid bytes alone don't establish which device or operation produced them.

## Hardware validation after capture review

Close the official app before launching a patched build. Test wired 809E first. Check scrolling before and after each operation: one side-button remap; middle click; a macro assignment; two manually selected profiles; automatic switching between two harmless apps; base-profile fallback; DPI buttons and overlay; exit/relaunch. Keep the official Restore as the recovery path. Don't test the unpatched executable again just to reproduce the known failure.

The packet writer restores NORMAL wheel rotation every time it writes a keymap. Custom wheel bindings aren't yet part of the profile model. Supporting them later means storing/validating two extra settings while leaving the 16 physical-button indices intact.
